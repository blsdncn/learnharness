# OpenAI-compatible endpoints: upstream precedent and lowest-friction scope

**Research date:** 2026-10-27  
**Question:** Which upstream direction is least controversial for adding generic OpenAI-compatible dictation and TTS endpoints, including speechifyd, while preserving Deepgram and leaving room for an ordinary OpenAI-compatible chat provider?

The strongest repeated request in this repository is a configurable OpenAI-compatible chat endpoint. Issues [#7](https://github.com/amosblomqvist/learnharness/issues/7) and [#30](https://github.com/amosblomqvist/learnharness/issues/30) are open and gather requests for a custom base URL, gateways, Requesty, Polza, and other compatible services. Their comments are user endorsements and use cases, not maintainer decisions. [#21](https://github.com/amosblomqvist/learnharness/issues/21) and [#29](https://github.com/amosblomqvist/learnharness/issues/29) request local models/Ollama; [#74](https://github.com/amosblomqvist/learnharness/issues/74) was closed by its author as a duplicate of existing requests ([comment](https://github.com/amosblomqvist/learnharness/issues/74#issuecomment-6389517930)). [#153](https://github.com/amosblomqvist/learnharness/issues/153) and [#215](https://github.com/amosblomqvist/learnharness/issues/215) respectively ask for custom providers and manual model IDs. This establishes demand, not agreement on one implementation.

The proposals split between a **general provider/model catalog** and **audio-specific endpoint settings**. PR [#40](https://github.com/amosblomqvist/learnharness/pull/40) proposes a broad local-server integration: protocol selection, endpoint model discovery, capability metadata and all model pickers. PR [#62](https://github.com/amosblomqvist/learnharness/pull/62) proposes a single configurable OpenAI-compatible provider registered in the usual model catalog; it has one blank APPROVED review by Hydrock ([review](https://github.com/amosblomqvist/learnharness/pull/62#pullrequestreview-5639375528)) and a later user request for a manual context fallback ([comment](https://github.com/amosblomqvist/learnharness/pull/62#issuecomment-6438562833)). A blank approval signals approval but gives no rationale or design guidance. PR [#57](https://github.com/amosblomqvist/learnharness/pull/57), another general endpoint implementation, is closed and unmerged; the fetched discussion had no explanation, so its closure should not be read as rejection. PR [#48](https://github.com/amosblomqvist/learnharness/pull/48) was explicitly closed by its author as superseded by #69 ([comment](https://github.com/amosblomqvist/learnharness/pull/48#issuecomment-6390002197)). PR [#103](https://github.com/amosblomqvist/learnharness/pull/103) adds one named OpenAI-compatible provider (Hyper); it is open with no maintainer review found. PR [#81](https://github.com/amosblomqvist/learnharness/pull/81) adds Ollama-specific model and search features; it is open with no review/comment found. An open PR, by itself, is not evidence of controversy.

Issue [#44](https://github.com/amosblomqvist/learnharness/issues/44) proposes inheriting Pi's provider and model configuration, including custom providers, OAuth and subscription logins. Its author explicitly connects this route to #7, #21 and #29; commenters support it, while one reports organization-login limitations ([comment](https://github.com/amosblomqvist/learnharness/issues/44#issuecomment-6391542142)) and another raises short-lived gateway-token needs ([comment](https://github.com/amosblomqvist/learnharness/issues/44#issuecomment-6404664577)). It is a substantially broader dependency and credential-lifecycle proposal, not a narrow audio endpoint precedent. Issue [#193](https://github.com/amosblomqvist/learnharness/issues/193) is closed as completed after its author linked [PR #161](https://github.com/amosblomqvist/learnharness/pull/161) as addressing it ([comment](https://github.com/amosblomqvist/learnharness/issues/193#issuecomment-6446278551)); #161 was still open when checked. The issue's state therefore does not establish that the proposed PR was merged or accepted.

For audio, [PR #203](https://github.com/amosblomqvist/learnharness/pull/203) is the closest precedent. It adds an OpenAI dictation choice while retaining Deepgram as default, reuses the OpenAI Platform key, and sends buffered audio to a fixed OpenAI transcription URL/model. Its description says it is open, and the fetched PR timeline and review list contained no maintainer comments or reviews. Treat that as no recorded feedback in the checked sources, not approval or rejection. The author notes that [#114](https://github.com/amosblomqvist/learnharness/pull/114) changes dictation language settings and overlaps in dictation/settings code; #203 and [#205](https://github.com/amosblomqvist/learnharness/pull/205) also share a settings-write serialization fix. The latter two PR descriptions say their branches merge cleanly together. This makes #203's audio and General-settings edits the likely integration seam to coordinate around. PR #114's timeline contained only a link to #101; no substantive maintainer response was found.

[Issue #15](https://github.com/amosblomqvist/learnharness/issues/15) directly requests selectable STT engines, provider/model/key/base-URL settings, optional authentication, no automatic cross-provider or paid fallback, reuse of 16 kHz PCM capture, and preservation of deferred transcript behavior and composer/question targets. It explicitly notes that batch transcription on Stop fits the current UX. Its acceptance criteria also require a local model to work with no API key or network. A generic endpoint can serve a genuinely offline model: LearnHarness does not need to know which backend serves it. Offline use should be validated against such a backend; a speechifyd test alone establishes compatible-server behavior. The issue additionally proposes shipping a local engine option, which is broader than adding configuration alone. The only fetched comment [requests AssemblyAI](https://github.com/amosblomqvist/learnharness/issues/15#issuecomment-6403056798); it does not establish maintainer preference. PR #203's description treats its fixed OpenAI implementation as a partial contribution toward #15.

The pinned [speechifyd README](https://github.com/blsdncn/speechifyd/blob/e385e69075b2624b1efadc25fe12d6a0a165f998/README.md#api) and [route implementation](https://github.com/blsdncn/speechifyd/blob/e385e69075b2624b1efadc25fe12d6a0a165f998/speechifyd/server.py) define standard `/v1/audio/speech` and multipart `/v1/audio/transcriptions` routes, with transcription returning `{text}`. The service uses Speechify's cloud services, so running its daemon locally does not satisfy #15's offline criterion. Earlier local source inspection confirmed that the upload handler requires Content-Length; a Node v24.18.0 HTTP probe confirmed that FormData with a known-size Blob sends it. This transport probe did not call a live transcription provider and does not establish maintainer approval.

## Chat catalog versus audio connections

A chat custom provider needs model identity and picker/catalog behavior, request protocol and capabilities, credential storage, and model selection across chat and background-agent roles. The broader PRs above address that model-registry problem. By contrast, speech synthesis and dictation need separately configurable service URLs and credentials, audio request/response handling, and their own failure behavior. The inspected checkout registers pi-ai built-ins in [src/agent/models.ts](https://github.com/amosblomqvist/learnharness/blob/77e1fd67ee2c0fadfc52907a307a89ee84387c06/src/agent/models.ts) and projects that catalog through [src/server/model-catalog.ts](https://github.com/amosblomqvist/learnharness/blob/77e1fd67ee2c0fadfc52907a307a89ee84387c06/src/server/model-catalog.ts); neither supplies an app-owned general custom-endpoint configuration to reuse. PR #203 is still a proposal, rather than an OpenAI dictation feature already present in this checkout. Its [route](https://github.com/ruspg/learnharness/blob/94cc03951b4ac571a1ed96d290af73a24ecb2b1b/app/api/stt/openai/route.ts) explicitly uses OPENAI_API_KEY and its [handler](https://github.com/ruspg/learnharness/blob/94cc03951b4ac571a1ed96d290af73a24ecb2b1b/src/server/openai-dictation.ts) pins the URL and model.

## Recommendation (inference, not maintainer consensus)

The **least controversial inference from the available evidence** is to keep the first upstream change additive and audio-scoped: generalize the existing OpenAI dictation choice with advanced endpoint fields, retain Deepgram as the selectable/default provider, and store dictation connection settings independently from TTS settings. Add TTS's OpenAI-compatible endpoint configuration separately, also with its own URL and credential. Do not add a third dictation provider mode: this follows the stated preference and avoids broadening #203 into chat model discovery. Keep the endpoint fields explicit and compatible with standard audio routes; speechifyd then fits through its OpenAI-compatible routes.

This recommendation is about limiting the first change's overlap and review surface. The requested deliverable remains audio integration; general chat-provider support was researched as related precedent. It should remain a separate model-catalog decision. The repository evidence does not identify a maintainer-endorsed winner among #62/#69, #44's Pi inheritance proposal, or the other chat approaches.

A practical staging sequence is: (1) reuse #203's WAV capture, final-frame flush, retry/discard, submit-success checks, and settings-write protections; (2) add advanced base URL, model, and endpoint-specific credential settings to its OpenAI selection while preserving Deepgram as default; (3) prepare TTS as a separately reviewable change using independent connection settings and standard `/audio/speech` requests. Keep OpenAI's ordinary setup working with its existing Platform key, and make a custom endpoint use its separately configured optional key. Avoid requiring voice/model discovery, account management, or a third dictation mode. This is a proposed revision for human approval, not an implementation already made or a maintainer-approved design.

## Evidence limits and open decisions

- No maintainer objection to the audio endpoint idea was found in the checked #203 comments/reviews; no recorded feedback is not approval.
- #57's unmerged closure has no fetched explanation. #62 has a blank approval but no substantive review rationale. #40, #69, #81, #103, #114, #161 and #205 had no substantive maintainer response in the fetched timelines/reviews.
- Existing user decisions: retain selectable/default Deepgram; configure TTS and dictation independently; use an API base URL including the version segment; keep TTS model/voice configurable; prefer advanced overrides for the OpenAI dictation option over a third mode. General chat-provider support and speechifyd account management are outside the audio implementation scope. Language-selection work in #114 should be coordinated with rather than folded into this change without approval.
- The revised plan still needs approval for the precise Advanced-settings and credential behavior, and for how to reuse the unmerged #203 code. No GitHub messages, merges, or application-code changes were made during this research.
